# Staff invitations

Gym owners can invite a user as `gym_admin` or `trainer`. The active gym is resolved from the signed-in session and its verified owner membership; request fields cannot select a gym or role outside this allowlist. Platform superadmin authorization remains separate. Gym admins can use the existing tenant APIs. Trainers can use only the dedicated trainer workspace API, which returns active assigned members and their attendance history; trainer membership is not accepted by the owner/admin APIs.

Invitations store only a SHA-256 token hash, expire after seven days, and are claimed in a MongoDB transaction with membership creation. A new account is created with the existing scrypt password hash. Existing accounts must be signed in as the invited email and their password is never changed. MongoDB deployments used for acceptance must support transactions. The user's existing single-active-gym tenant resolver means an account with another active gym membership will not gain a usable multi-gym session from this invitation.

There is no email delivery integration. Invitation creation returns a one-time acceptance URL to the authenticated owner, who must share it privately with the invitee. The URL is a bearer secret and should be treated as sensitive; it expires after seven days and becomes unusable after acceptance or revocation. Production email delivery is not configured, so invitations are not sent automatically.
