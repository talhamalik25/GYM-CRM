# Fitivo: document alignment audit

Date: 2026-10-31 (Asia/Karachi). Evidence: existing working-tree source, all six governing documents, route/model inventory in PRODUCT_SPEC.md, and checks recorded below. This is a bounded source/runtime audit, not a penetration test or proof of launch readiness. Application code, APIs, models, authentication and existing data were not changed.

## Assessment

The project already implements substantial tenant-aware operations. Preserve that foundation. It does not yet deliver the documented retention/WhatsApp/cash-accountability MVP, and current role/price rules conflict with the security contract. Existing uncommitted styling work was present before the audit; findings describe that working tree, not only HEAD. No evidence establishes a successful full month of real-gym use.

Severity: **Critical** = security/financial-integrity exposure requiring resolution before real use; **Important** = missing MVP behavior, operational reliability or professional quality; **Minor** = documentation/maintainability discrepancy. Evidence confidence is stated separately; a source finding is not a claimed successful exploit.

## Critical findings

### C01 — Staff can set membership charges independently of database plan prices

`app/api/subscriptions/route.js:88` and `app/api/subscriptions/[id]/renew/route.js:65` use `body.agreedPrice ?? plan.price`. Their default `requireApiUser` permits both gym_owner and gym_admin. A valid positive integer of 1 can replace a higher plan price; server validation checks format but does not enforce the documented server-owned price or an owner-approved discount policy. Subsequent dues correctly follow the stored snapshot, but that snapshot originated from the client override. Conflicts with AGENTS.md client-price prohibition and SECURITY.md money rules. Static path confirmed; no financial records created. Recommended fix: derive price from the tenant plan, or explicitly approve and document a constrained owner-only discount workflow before implementing it.

### C02 — Owner-only plan/report permissions are not enforced

`lib/auth.js:107` defaults to gym_owner/gym_admin. `app/api/plans/route.js` POST, `plans/[id]/route.js` PATCH, `reports/route.js` GET and `payment-reports/route.js` GET use that default. Staff can therefore modify pricing or view owner-only reports when their plan entitlement permits it. Export GET also allows gym_admin and deserves an explicit product permission decision. Existing server role checks are present, but implement the wrong matrix. SECURITY.md §3 explicitly limits plan management/reports to owners. Static evidence; authenticated role matrix not exercised against MongoDB. Recommended fix: explicit method-level roles and negative owner/staff/trainer tests.

### C03 — Member money and edits have no required accountability trail

`models/Payment.js` has no receivedBy, voided/voidedBy/reason or reference; `models/Attendance.js` has no markedBy. No AuditLog model, write helper, endpoint or viewer exists. Payment creation and member PATCH cannot satisfy SECURITY.md §5 or PRD cash accountability. `app/api/payments/[id]/route.js` only exports GET: a safe correction/void workflow is absent. No member-payment hard-delete API was found, which is positive; absence of deletion is not implemented voiding. PlatformInvoice has its own actor/void/claim history and does not cover member money. Recommended fix: preserve existing records, add backward-compatible actor/void/audit support, then test balances, reports and receipts after voids. Never backfill fictional historical actors.

### C04 — Public registration lacks abuse throttling when enabled

`app/api/auth/register/route.js` validates origin, bounded JSON and identity, but has no rate limiter before index work, password hashing and transactional account creation. Eligibility history prevents reuse of the same email/slug, not requests with new identities. `staff/invitations/accept/route.js` also has no throttle (high-entropy token and single-use transaction are protective). Login has a shared DB limiter, but it is only per normalized email, so varying identities bypasses a global request budget. SECURITY.md §§2/8 require sensitive/public throttling. No load attack performed. Recommended fix: bounded, shared abuse controls before expensive work; test limits without relying on spoofable headers. Contact/trial pages currently have no server submission endpoint to rate-limit.

## Important findings

- **I01 — Core differentiators absent.** No member `wa.me` template/PK number normalization, reminder-click log, configurable absent-in-N-days query or retention view. Dues/expiry lists are real, but lack follow-up actions. PRD §§4–5 and PRODUCT_DETAIL core promise are unmet. `isActive` denotes account status, not missed attendance.
- **I02 — Basic-plan dashboard requests an unavailable feature.** `components/dashboard/owner-dashboard-analytics.js:141` requests `/api/reports?dashboard=1`; `lib/routeEntitlements.js` treats every reports request without `basic=1` as advancedAnalytics. `lib/saasPlanRules.js` gives Basic basicDashboard but not advancedAnalytics. Expected result from code is 403/error panels for Basic dashboard analytics. Not reproduced with a live tenant. Resolve this without granting the entire advanced-report endpoint to Basic. Dashboard also emphasizes members/active memberships/check-ins/dues rather than the specified today/month collections summary.
- **I03 — Trial and billing contracts disagree.** Marketing site config offers an approval-based 14-day trial; `lib/gymOwnerRegistration.js`/registration route immediately grant seven days when enabled. Contact/free-trial forms only prepare a mailto draft. `/payment` has local screenshot preview and disabled submission; no private upload storage, request queue or screenshot association exists. Preserve honest UI copy and settle one flow before backend changes. PRD §6 puts subscription billing after MVP, while PRODUCT_DETAIL lists it in MVP; this scope conflict needs Talha's decision, not a silent rewrite.
- **I04 — Trainer attendance permission missing.** All attendance handlers use owner/admin defaults; trainer workspace GET is read-only. SECURITY.md grants trainers attendance marking. Define assigned-member restrictions and then implement/test the permitted subset; do not simply open the entire attendance directory.
- **I05 — Input bounds are inconsistent.** `lib/memberApiHelpers.js` accepts unbounded fullName/notes/email lengths, and `lib/planApiResponse.js` accepts unbounded name/description and extremely large safe-integer duration/price values. Corresponding model fields do not consistently cap them. Most tenant handlers use `request.json()` rather than the byte-limited helper used by auth/profile/invitation acceptance. This can produce excessive storage/work and invalid business dates. Field allow-lists, ObjectId checks and enum/type checks already exist: extend them, do not replace them wholesale. Cross-tenant ownership is checked for referenced member/plan/trainer IDs in principal flows.
- **I06 — Source-level tenant guard exceptions need closure/tests.** Core queries use `tenantFilter`, `getRequestScope`, gym-scoped aggregates and scoped population. However, member creation at `app/api/members/route.js:105` populates plan/trainer without `match: gymId` after prior scoped validation. Invitation acceptance writes by invitation `_id` at `app/api/staff/invitations/accept/route.js` without gymId after resolving a hashed bearer token. These break the literal all-tenant-query rule but do **not** establish a cross-tenant exploit: references/token were validated earlier. Add defense-in-depth scopes and corruption/foreign-reference tests. Platform-admin global queries, global identity/session lookup, and resolving the authenticated membership's Gym root are intentional trust boundaries, not automatically tenant leaks. Existing integration suites were not executed; every-resource isolation remains unproved.
- **I07 — Several protected pages rely on API rejection rather than page-level role checks.** `requirePublicGymOperationalPage` handles public-trial redirects and does not fully authorize every role/legacy gym. Settings, staff, profile and branches can render a shell to a signed-in non-owner and rely on APIs to deny data/actions. Billing/admin/trainer have stronger explicit page checks. SECURITY.md asks for both. No protected-data leakage is asserted from shell rendering alone.
- **I08 — Operational prices are unconfirmed source defaults.** `lib/saasPlanRules.js` initializes real catalog entries at PKR 2999/5999/9999, while public config has null prices and documents call commercial terms unconfirmed. Not an exposed secret or a client repricing bug; it is an owner-confirmation/config-location gap. Preserve historical snapshots. Bank placeholders are correctly labeled and no real bank credentials were found in components.
- **I09 — Presentation is inconsistent and not fully validated.** Global tokens use canvas #FAFAFB, success #166534, warning #92400E and danger #991B1B versus the draft's #F8FAFC/#16A34A/#D97706/#DC2626. Inter is loaded centrally, while marketing hero accents use Georgia/Times New Roman (`marketing-home.module.css:82`, `marketing-pages.module.css:45`). Marketing duplicates muted/background colors and has gradients/shadows; the app uses separate legacy dashboard selectors. DESIGN_SYSTEM explicitly says existing exact values take precedence: this is a reconciliation task, not permission to restyle. Public payment, demo, privacy, terms and workouts expose unfinished placeholders/notices; these are concrete launch-quality gaps, not an unsupported aesthetic verdict about every page. Authenticated page screenshots and AA contrast were not verified.
- **I10 — Legacy CSS and duplicate component families remain.** Global CSS is 11,394 lines; three marketing modules total 3,037 additional lines. Page-level dependency amounts are in PRODUCT_SPEC.md. This is not all active legacy CSS: theme/reset/token lines are included. `page-heading`/`page-header`, `badge`/`status-badge`/`status-pill`, `table`/`data-table`, `field`/`control`/`input` form overlapping API families. Many are intentionally wrappers; duplication should be reviewed by use, not mass-deleted. Long literal `exact:` Tailwind class lists preserve values but scatter raw colors instead of semantic tokens. Membership record forms use local input/button markup instead of shared controls. Static inline styles remain in the workouts icon (`fontSize: 28`) and report chart wrapper (`width: "100%"` mixed with dynamic height); genuine chart dimensions/colors are dynamic and are not blanket violations. Migration remains paused.
- **I11 — Tests do not establish definition of done.** One existing unit source assertion fails; eight database suites are skipped. Tests include valuable mocked auth/tenant behavior and financial rule checks, but also regex assertions over source. No full authenticated member → subscription → payment → receipt → attendance flow, live concurrency, role matrix, expiry cron or backup restore was exercised. Build/lint results below are separate from functional proof.
- **I12 — Seed scripts can target an active real gym.** `scripts/seedTenant.js` requires an active GYM_ID and checks missing legacy ownership, but does not enforce a disposable database/fixture marker. `scripts/seed-payments.js` selects the first three members of that gym and creates sample financial records; `seed-attendance.js` likewise operates on tenant members. This risks contaminating real records if an operator points it at production. Not executed. Add explicit disposable-environment protection before any future demo seeding; do not delete existing records in this audit.

- **I13 — Dependency advisory requires review.** The successful npm audit reports 16 moderate affected packages in the ESLint chain, driven by minimatch globparts amplification ([GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249)). No high/critical findings reported. This is primarily tooling exposure in this dependency report, not a demonstrated remote app exploit. Review a compatible dependency update separately; do not run a forced major upgrade during the audit.

## Minor findings

- **M01 — API error contract differs.** Actual common errors are `{success:false,error:{message,fields?,context?}}`, not the architecture's string error. Existing clients expect the object. Preserve compatibility and document it in a later authorized architecture update.
- **M02 — Environment template incomplete.** Missing public support variable names; existing defaults violate literal names-only guidance. Test and migration variable setup lives elsewhere. No new env vars added here, so template remains unchanged.
- **M03 — Architecture model/index draft is stale.** Global User/Session/RateLimit/Settings/catalog models intentionally lack gymId; `GymMembership` handles access; `Subscription` handles purchased membership. Gym is its own root. Legacy tenant schemas permit existing unowned documents; no live inventory was run. Many recommended compound date indexes are missing in source. Do not rename collections or backfill ownership blindly.
- **M04 — Naming and layout differ from suggested folders.** `(dashboard)` replaces `(app)`; `components/layout`, resource-specific folders and `lib/*Rules.js` replace a consolidated `components/app` and `lib/validators`; marketing config lives in lib. ARCHITECTURE explicitly permits existing conventions. These are documentation differences, not reasons to restructure working code.
- **M05 — Technical debt comments and visible deferred scope.** Marketing bank/site/inquiry/payment files contain TODOs explaining absent backend flows. They are disclosure comments, not secret debug endpoints, but fall short of the strict no-TODO convention. `/workouts`, implemented multi-branch and advanced SaaS/trainer work exceed the current draft MVP. Prior authorization history is unknown; do not claim earlier agents acted without approval or remove working features.

## Recommended order of fixes

1. Settle the owner/staff/trainer matrix and server-owned pricing contract; fix C01/C02 and test negative access cases without changing auth architecture.
2. Add backward-compatible member payment actor attribution, void and AuditLog support (C03); exercise concurrent installments, retries, void totals and historical-record behavior in an isolated database.
3. Close public abuse/input limits and tenant-scope exceptions (C04/I05/I06); run every-resource cross-tenant and role integration tests, preserving all existing data.
4. Repair Basic dashboard entitlement use and implement the exact daily collections/expiry/dues summary; verify Basic and higher plans.
5. Implement MVP reminder links/logging and configurable retention lists; normalize Pakistani numbers and test staff click behavior.
6. Reconcile trial duration/approval and confirmed commercial terms with Talha; finish only the approved trial/billing scope, including private screenshot handling if retained in MVP.
7. Address missing member lifecycle/contact fields and trainer attendance permissions through explicit backward-compatible tasks.
8. Fix stale tests, exercise all real flows on isolated fixtures, verify 375/768/1280 layouts, keyboard/dialog/error/empty states and deployment/backup procedures. Improve only the affected screens with Tailwind; do not resume mass CSS migration.
9. Reconcile remaining architecture/design/config documentation and freeze deferred scope. Do not build workouts, import, branches or other later features as part of these fixes without a separate task.
